# Ireland Job Radar

Ireland Job Radar is a Republic-of-Ireland job discovery and prioritisation system designed to find vacancies from original employer sources, normalize them into one dataset, track changes over time, and help surface jobs that are most relevant to the candidate profile.

The project follows one rule throughout the pipeline:

> **Collect broadly. Normalize centrally. Personalize at ranking time.**

## Current operating model

As of 22 August 2026, the master registry contains **600 employers**, of which **250 are active** in the scraping universe and **350 remain available as reserve candidates**. The active registry is deliberately curated for Republic-of-Ireland relevance, source reliability, and profile-relevant return on scraping effort.

The GitHub Actions refresh workflow is scheduled for **every 15 minutes**. Scheduled Actions can start late during busy periods, so 15 minutes is a target cadence rather than a hard real-time guarantee.

## What the system does

The pipeline combines direct employer sources, ATS APIs, rendered careers pages, and company-specific connectors. Jobs are normalized into a common structure, restricted to Republic-of-Ireland opportunities, deduplicated, enriched with recency and profile metadata, and written to `data.json` for the browser dashboard.

The dashboard supports free-text search and filters for company, location, sector, source, posting age, employment type, experience level, new postings and visa/sponsorship evidence. The **Match my profile** toggle uses the backend `candidate_match_score` and currently treats scores of **55+** as profile matches.

## Employer registry

The source of truth for the employer universe is:

`ireland_job_radar_HARSHIT_MASTER.csv`

The important control column is:

`include_in_scrape_registry`

Only enabled employers participate in the active scrape. Inactive employers remain in the CSV so they can be tested or swapped in later without rebuilding the registry.

Registry changes are kept separate from generated scrape outputs. A company should normally be activated only after its Republic-of-Ireland job source is verified, while removals should favor employers that have no current live jobs, no profile-relevant output and no proven working history.

## Connector architecture

The scraper supports a mixture of reusable ATS adapters and targeted company connectors. The exact set evolves as employers change platforms.

Examples currently verified or specifically repaired in this project include:

- **Oracle** — Oracle Recruiting Candidate Experience / HCM REST API, with Ireland location filtering.
- **IBM** — official IBM careers search and Ireland vacancy detail verification.
- **Marsh McLennan** — official careers source retained as the active MMC entity; duplicate Mercer coverage is disabled.
- **Cubic³** — Ashby job-board API.
- **Version 1** — SmartRecruiters API.
- **McKinsey & Company** — official source with a previously verified-job fallback when the live site blocks or times out.
- **Gong** — verified Dublin job-level source.

Reusable platform support also includes ATS families such as Workday, Greenhouse, Lever, Ashby, SmartRecruiters, Pinpoint and other source-specific adapters present in `scrape.py`.

A connector returning zero jobs is not automatically treated as a trustworthy zero. The system distinguishes genuine zero-vacancy states from broken or unverified connectors through coverage diagnostics and company history.

## Data flow

1. Read the active employer registry.
2. Query direct/ATS/company connectors.
3. Keep genuine Republic-of-Ireland opportunities.
4. Normalize titles, locations, employment metadata and source fields.
5. Deduplicate equivalent vacancies.
6. Compare against historical jobs and mark newly discovered vacancies.
7. Calculate discovery and profile-ranking metadata.
8. Classify current-job visa/sponsorship language.
9. Update employer sponsorship history from unique postings.
10. Attach official employment-permit history where available.
11. Write dashboard data and diagnostics.

## Profile matching

Profile matching is metadata, not a collection restriction. A job should not be deleted simply because it has a low candidate score.

The backend profile is loaded from `profile.json`. The scoring pipeline uses evidence such as role-family fit, skills, experience requirements and location. Relevant output fields can include:

- `candidate_match_score`
- `match_reasons`
- `matched_skills`
- `missing_skills`
- `experience_fit`
- `role_family`
- `role_tier`

The dashboard's **Match my profile** control filters on the existing score rather than creating a second ranking model in the browser.

## Visa and sponsorship intelligence

Visa information is intentionally split into three different kinds of evidence because they answer different questions.

### 1. Current vacancy wording

Each job is scanned for explicit sponsorship or work-permit language. Negative phrases are evaluated before positive phrases so text such as “no visa sponsorship” is never misclassified as supportive.

A vacancy can be classified as:

- `sponsors`
- `no_sponsorship`
- `not_mentioned`

When explicit text is found, the scraper stores a short evidence snippet so the dashboard can show why the job received that status.

### 2. Employer sponsorship history

`sponsorship_history.json` tracks **unique postings**, not every 15-minute scrape occurrence. This prevents the faster refresh frequency from artificially inflating employer history.

Employer history can summarize whether sponsorship language has appeared frequently, occasionally, rarely, explicitly negatively, or whether there is not enough evidence yet.

Silence is kept neutral: a job that does not mention sponsorship is not treated as proof that sponsorship is unavailable.

### 3. Official Irish permit history

`official_permit_stats.json` contains employer-level historical employment-permit evidence produced by `visa_stats.py` from official Irish government permit statistics.

This is historical evidence, not a guarantee that a particular current role will sponsor a permit. It is intended as an additional prioritisation signal.

The dashboard can therefore distinguish:

- current job explicitly mentions sponsorship;
- employer has prior sponsorship-language history;
- employer has an official permit record;
- current job explicitly rules out sponsorship;
- current job is silent on sponsorship.

## History and diagnostics

The project stores history so a single failed scrape does not erase knowledge about a working employer or a previously seen vacancy.

Important concepts include:

- **New since last check** — a newly discovered vacancy compared with persisted seen-job state.
- **Proven working** — a company/source that has successfully produced valid jobs historically.
- **True zero** — a verified/proven source currently has zero qualifying Ireland jobs.
- **False zero / broken** — an automatic source currently reports zero but that result is not trusted.
- **Manual search needed** — no working job-level connector is currently available.

These diagnostics are important when maintaining the 250-company active set: “zero jobs” alone is not enough evidence to remove a valuable employer.

## Dashboard behavior

The dashboard is a static frontend that loads `data.json`. It supports:

- original-source application links;
- broad keyword/company/skill search;
- company, location, sector and source filters;
- posting-age filters;
- employment type and experience-level filters;
- new-posting filtering;
- visa/sponsorship filtering;
- **Match my profile**;
- saved jobs and application tracking;
- live-company and connector-diagnostic views.

The company filter should remain limited to the curated working/careers-page universe rather than the full 600-company reserve registry.

## Refresh cadence

The main workflow is configured as:

```yaml
schedule:
  - cron: '*/15 * * * *'
```

This requests four refreshes per hour. GitHub does not guarantee exact start times for scheduled workflows, so a run can be delayed.

A faster scrape cadence makes persistent history more important: all longitudinal counters should be based on unique jobs or explicit observations, not raw run count.

## Running locally

Typical local checks:

```bash
python3 -m py_compile scrape.py
python3 scrape.py
```

For targeted connector work, use the project's targeted environment variables or direct function tests rather than running the full scraper when a single source is being repaired.

For official permit data:

```bash
python3 visa_stats.py
```

The exact dependencies vary by connector. Common dependencies include Python 3, `requests`, `pandas`, `openpyxl` and Playwright for JavaScript-rendered sources.

## Safe development workflow

Because automated refresh commits can land on `main` while local connector work is in progress, always check synchronization before committing:

```bash
git fetch origin
git status -sb
git rev-list --left-right --count HEAD...origin/main
```

If the working tree is clean and the branch is only behind, fast-forward first:

```bash
git pull --ff-only origin main
```

Before pushing a manual change, fetch again and make sure the remote did not advance while you were testing.

Generated data refreshes should not be overwritten by an older local copy of `data.json`, `seen_jobs.json` or ATS caches.

## Validation before commit

For scraper/UI changes, the minimum checks are:

```bash
python3 -m py_compile scrape.py
git diff --check
git status -sb
git diff --stat
```

For registry changes, also verify:

- master registry total remains **600**;
- active registry remains **250**;
- intended additions/removals are exactly the expected companies;
- known working/high-value sources are not accidentally disabled.

For connector repairs, test the connector directly and verify real Republic-of-Ireland job-level output before calling it proven.

## Design principles

- Prefer original employer/ATS sources over aggregators.
- Keep Republic-of-Ireland scope strict; do not count Belfast/Northern Ireland as ROI.
- Keep collection broad and ranking personal.
- Never equate an unverified zero with “no jobs”.
- Preserve historical evidence across refreshes.
- Treat sponsorship evidence as probabilistic/historical unless the current vacancy states it explicitly.
- Do not overwrite fresh automated data while applying code changes.
- Keep the 250-company active registry focused on useful, working sources while retaining the full 600-company reserve universe.
